STORY FILTERING VISUAL GUIDE
============================

┌─────────────────────────────────────────────────────────────────────────────┐
│                     STORY VISIBILITY DECISION TREE                          │
└─────────────────────────────────────────────────────────────────────────────┘

                              Start: Is Story Visible?
                                        |
                        ┌───────────────┼───────────────┐
                        │               │               │
                   Is Own Story?    Is Blocked?    Story Status?
                     /   \           /    \         /    |    \
                   YES   NO         YES   NO    APPROV  PEND  UPLOAD
                    |     |          |     |      |      |      |
                   YES   NO        HIDDEN| NO     |      |    ONLY
                        |              |         YES    ONLY CREATOR
                        │              │          |   PARENTS  CAN SEE
                        │              │          │      |
                        │              │          YES    PARENT?
                        │              │          │      / \
                        │              │         YES   YES NO
                        │              │          |     |   |
                        └──────────────┴──────────┴─────┴───┴───→ RESULT

Result:
  YES  = Story visible to user
  NO   = Story not visible to user


┌─────────────────────────────────────────────────────────────────────────────┐
│                        CONTACT TYPES (Whitelist)                            │
└─────────────────────────────────────────────────────────────────────────────┘

User A's Contact List Includes:

1. APPROVED BIDIRECTIONAL CONTACTS
   ┌────────────────┐
   │ contacts coll. │
   └────────────────┘
   {
     users: ["user_a", "user_b"],  ← alphabetically sorted
     status: "approved"
   }
   
   → User A can see approved stories from User B
   → User B can see approved stories from User A
   → BIDIRECTIONAL: Both must approve


2. LINKED CHILDREN (If User A is Parent)
   ┌────────────────┐
   │ users/{parent} │
   └────────────────┘
   {
     linkedChildrenIds: ["child_1", "child_2", "child_3"]
   }
   
   → Parent can see ALL story statuses from children:
     - approved (feed)
     - pending (for approval)
     - rejected (show rejection)
   → ONE-DIRECTIONAL: Parent has authority


3. LINKED PARENTS (If User A is Child)
   ┌────────────────┐
   │ users/{parent} │
   └────────────────┘
   {
     linkedChildrenIds: ["user_a", ...]
   }
   
   → Parents can see User A's stories
   → User A can also see parent's approved stories
   → Found via: users where linkedChildrenIds contains user_a


┌─────────────────────────────────────────────────────────────────────────────┐
│                       DATA FLOW: Story Display                              │
└─────────────────────────────────────────────────────────────────────────────┘

USER OPENS APP
    │
    ├─→ ContactRepository.getContactIds()
    │   ├─ Query: contacts where status='approved'
    │   ├─ Query: users where linkedChildrenIds contains self
    │   ├─ Query: own linkedChildrenIds
    │   └─ Result: Set<String> of contactIds
    │
    ├─→ StoryStreamManager.getStoriesFromWhitelist()
    │   ├─ Firestore Query: stories where userId IN contactIds
    │   ├─ Filter: status == 'approved'  ← Firestore level
    │   └─ Result: List<Story> from Firestore
    │
    ├─→ StoryStreamManager._filterStoriesByVisibilityRules()
    │   ├─ Get block statuses (batch query)
    │   ├─ Get parent-child relations (batch query)
    │   └─ For each story:
    │       └─ Apply _canUserSeeStoryOptimized() logic
    │           ├─ Own story? → YES
    │           ├─ Blocked? → NO
    │           ├─ Status check:
    │           │  ├─ APPROVED → YES (if not blocked)
    │           │  ├─ PENDING/REJECTED → YES if parent
    │           │  └─ UPLOADING → NO (except creator)
    │           └─ Return: bool (visible or not)
    │
    ├─→ StoryRetrievalService.getStoriesFromWhitelist()
    │   └─ Returns Stream<List<UserStories>> (filtered)
    │
    └─→ UI/Controllers Display Stories

┌─────────────────────────────────────────────────────────────────────────────┐
│                     STORY STATUS TRANSITIONS                                │
└─────────────────────────────────────────────────────────────────────────────┘

    │
    ├─→ UPLOADING (uploading to Storage)
    │       │
    │       ├─→ Storage upload succeeds
    │       │       │
    │       ├─→ PENDING (waiting for parent approval)
    │       │       │
    │       ├─→ Parent approves? ──YES──→ APPROVED (visible in feed)
    │       │                                 │
    │       │                                 ├─→ Expires after 24h
    │       │                                 │    (still in profile if permanent)
    │       │                                 │
    │       │                                 └─→ User saves to profile
    │       │                                      (visibility: permanent)
    │       │
    │       └─→ Parent rejects? ──YES──→ REJECTED (shows rejection reason)
    │                                         │
    │                                         └─→ Expires after 24h
    │
    └─→ Upload fails? → UPLOADING (with uploadError field)


┌─────────────────────────────────────────────────────────────────────────────┐
│                    BLOCK STATUS CHECKING                                    │
└─────────────────────────────────────────────────────────────────────────────┘

User A and User B

Option 1: A blocks B
    A's view: Can't see B's stories
    B's view: Can see A's stories (unaware of block)
    
Option 2: B blocks A
    B's view: Can't see A's stories
    A's view: Can see B's stories (unaware of block)
    
Option 3: Both block each other
    A's view: Can't see B's stories
    B's view: Can't see A's stories


Firestore Check:
    IF (blocked_contacts/A_B exists) OR (blocked_contacts/B_A exists)
    THEN hide stories from both users


┌─────────────────────────────────────────────────────────────────────────────┐
│                    PARENT-CHILD RELATIONSHIP                                │
└─────────────────────────────────────────────────────────────────────────────┘

Parent View:
    └─ Can see ALL child stories:
       ├─ APPROVED (in feed)
       ├─ PENDING (for approval decision)
       └─ REJECTED (show rejection)

Child View:
    └─ Can see ONLY parent's APPROVED stories
       (treat parent like approved contact)


Linked by:
    Parent Document:
    {
        id: "parent_123",
        linkedChildrenIds: ["child_1", "child_2"]
    }
    
Query to find parent:
    SELECT * FROM users WHERE linkedChildrenIds CONTAINS "child_1"


┌─────────────────────────────────────────────────────────────────────────────┐
│                      CORRECT FILTERING RULES                                │
└─────────────────────────────────────────────────────────────────────────────┘

APPROVED CONTACTS (bidirectional):
  Can see stories if:
    ✓ Story status = APPROVED
    ✓ No block between users
    ✓ Story not expired
    ✓ Story visibility = TEMPORARY (feed) or PERMANENT (profile)

PARENT-CHILD:
  Parent can see stories if:
    ✓ Any story status (APPROVED, PENDING, REJECTED)
    ✓ No block between users
    ✓ Story not expired
    ✓ Child is in parent's linkedChildrenIds
    
  Child can see parent stories if:
    ✓ Parent story status = APPROVED
    ✓ No block between users
    ✓ Story not expired

OWN STORIES:
  ✓ Creator can always see their own stories
  ✓ Regardless of status or visibility
  ✓ (but can't see uploading stories from others)


DENIED:
  ✗ Stories from non-contacts
  ✗ Stories with status = UPLOADING (except creator)
  ✗ Expired stories (>24 hours old)
  ✗ Stories when users are blocked
  ✗ Stories with visibility = ARCHIVED
  ✗ GROUPS ARE NOT A FILTERING CRITERION!

┌─────────────────────────────────────────────────────────────────────────────┐
│                    PERFORMANCE CONSIDERATIONS                               │
└─────────────────────────────────────────────────────────────────────────────┘

Firestore Query Limits:
  - whereIn() max 10 items: handled with chunking
  - arrayContains: used for approved contacts
  - compound queries: contact + status filters

Optimization:
  - Batch load parent-child relations (parallel queries)
  - Batch load block statuses (parallel queries)
  - Cache contact IDs (10 minute TTL)
  - Cache parent-child relations (10 minute TTL)

Preloading Strategy:
  - Should preload from contactIds (not groups)
  - Limits to 5 upcoming stories
  - Max 3 concurrent downloads
  - 2 minute timeout per story
